## 게임 콘셉트

- 싱글: 짜증나는 일상 속에서 시작한 난동이 경비·경찰·상위 대응까지 확대되는 자유 물리 블랙코미디. 고정 퀘스트/장편 스토리가 아니다.
- 멀티: 싱글의 타격/물리/NPC/대응을 재사용하는 협동 난장판, 은행 소동 같은 공동 목표.
- 재미의 중심: **시나리오적 상황과 NPC의 반응이 다르기 때문에 같은 간단한 액션이 매번 다른 경험이 된다**.
- 각 싱글 시나리오에는 **선택형 고유 추가 시나리오(고득점 루트)** 한 개 정도. 회사원 예시는 사장실 인질극.
- 첫 플레이는 감정이입, 재플레이는 즉시 행동 가능하게. 긴 강제 컷신과 대사 퍼즐 지양.

## 반드시 풀 문제: 시작 직전과 첫 행동의 반응

단순히 등장인물의 초반 대사를 작성하지 말고, 모든 시나리오에 다음을 작성하라.

- 플레이 가능 상태의 **평상시 대사와 얄미운 행동**: NPC가 어떤 이유로 화를 돋우는가?
- 플레이어가 처음 저지르기 쉬운 **대표 행동 트리거**: 무엇을 치고/던지고/부수는가?
- 이를 본 주변 NPC의 **정해진 리액션 비트**: 인물별 대사, 표정, 동작, 접근/도주, 순서, 짧은 지연.
- 대표 행동 대신 즉시 공격하거나 이탈하는 경우의 **대체 반응**.
- 반응 중 피격·이동·경비 출동·반복 행동이 생길 때의 **중단/전환 규칙**.
- 도망간/이전에 시비를 건 NPC가 나중에 재등장할 때 **기억과 연속성**을 유지할지 최소 비용으로 판단.
- 멀티에서는 두 사람이 동시에 촉발하거나 둘 다 잔소리를 듣는 경우의 연출/중복 억제.

**골든 샘플:** 기존 회사원의 책상 내려치기(첫 B, 반복 A) → 박 대리 "왜 그래?" → 김 팀장 빼꼼 "뭐야 무슨 소리야?" → "이게 무슨 짓이지?" → 가까이 접근·잔소리. 이 장면의 순서를 보호하라.

## 작업 산출물

1. **Scenario Design Principles:** 도입 마찰·첫 돌발행동·세계 반응·선택형 루트의 공통 문법.
2. **Reaction Event Template:** 트리거/조건/주체/대상/대사/몸짓/우선순위/인터럽트/폴백/한 번만/협동 대응까지 포함한 데이터 템플릿.
3. **회사원 시나리오 풀 설계:** 기존 반응 보호; 건물/층 이동·경비 수색·경찰 도착 연출·사장실 특별 루트와 결말. **기존 구현과 추가 설계를 명시적으로 분리**.
4. **자영업자 시나리오 풀 설계:** 시장 출근길 NPC 마찰부터 가게 진상 손님, 플레이어 첫 행동, 주변 상인 반응, 공간 확장, 회사와 다른 고유 특별 루트.
5. **공무원/교통사고/야구:** 같은 템플릿으로 각각 짧은 시나리오 청사진. 특별 루트는 서로 다른 상호작용 구조가 되게 제안.
6. **Score Decision:** 기존 누적 피해액($) 장부를 보존하면서 '특별 루트 고득점'을 만드는 2~3개 안 비교. 임의의 가짜 보너스 달러를 확정하거나 기존 HUD를 멋대로 바꾸지 마라.
7. **Single–Coop Reuse Matrix:** 반응/NPC/물리/경찰/특별 이벤트 중 재사용과 새 구현을 분리. 온라인 물리 동기화는 별도 위험으로 평가.
8. **Implementation Slices & Playtest Gates:** 기존 시나리오의 짧은 도입·첫 행동·반응 → 경비·신고 → 고유 루트 검증 순서. 인간 검수는 대표 시퀀스 소수로 최소화.

## 설계 품질 기준

- 시스템을 계속 늘리지 말고 기존 상호작용·NPC 상태와 데이터 조합을 우선.
- 한 시나리오당 강제 이벤트만 늘리는 단선형 스토리가 되지 않도록 할 것.
- 모든 설계안에 '재미 이유 / 재사용 요소 / 신규 작업 부담 / 실패 가능성 / 검증 방법'을 제시.
- 시나리오별 도입 대사 5개를 쓰는 것이 목표가 아니다. **플레이어가 행동했을 때 누가 어떻게 반응하는지**를 재미있게 설계하는 것이 목표다.
- 지엽적인 결정을 사용자에게 물어보지 말고 PROPOSED 가정으로 판단하되 미확정으로 남겨라.
- 성인 풍자 만화형의 비고어 슬랩스틱 톤 유지. 실제 범죄 실행 방법의 고증은 불필요.
- **이번 턴은 설계 작업만 하라. Godot 코드/기존 실행 씬/승인 자산을 변경하지 마라.** 별도 문서 초안 또는 제안 PR로 제출하고 완료/테스트를 허위 주장하지 마라.

최종 보고는 '사용자 결정 필요 3개 이하 / 구현 선행 조건 / 다음 구현자에게 바로 줄 명령'으로 간결하게 끝내라.
